# E2E-тесты

## Описание

Канон сквозного теста **AEM**: система проверяется целиком как чёрный ящик —
запрос уходит в точку входа FastAPI, проходит middleware, сценарии и адаптеры, а
утверждения ставятся над ответом и над состоянием базы. Тест воспроизводит
многошаговый сценарий реального пользователя, а не один вызов.

Это самый дорогой уровень: он запускается реже остальных и должен падать
только по настоящей причине — нарушенному контракту с клиентом.

## Как это работает

### Обязательные сценарии

| Сценарий | Шаги | Что подтверждается |
| --- | --- | --- |
| Жизненный цикл сессии | регистрация → вход с получением Bearer-пары → продление сессии → выход с отзывом refresh-токена | форма токенов в теле, срок жизни, отзыв: продление после выхода невозможно |
| Избранное | вход → добавление тайтла в избранное → список избранного → удаление | запись прошла в базу, snapshot вернулся из локальных данных, права проверены |
| Владение ресурсом | аноним → `401`; пользователь A к ресурсу пользователя B → `403` | матрица маршрутов соблюдается на живом HTTP, а не только в коде маршрута |
| Умный поиск и воспроизведение | семантический запрос к эндпоинту поиска → выбор тайтла → получение момента → запрос потока через `/media-proxy/...` → проверка чанков и заголовков | цепочка «LLM → каталог → провайдер → прокси» работает без обращения в интернет |
| Хайлайт от захвата до ленты | публикация момента → появление в публичной ленте → лайк → счётчик в карточке | инвалидация кэша ленты действительно видна следующему читателю |
| Профиль и видимость | изменение статуса и флагов видимости → публичная страница другого пользователя | приватные секции скрыты, публичные присутствуют |

### Принципы

**Транспорт — `httpx.AsyncClient` над ASGI-транспортом.** Клиент упирается
прямо в точку входа приложения: маршрут, middleware заголовков, CSRF, сессия и
обработчики ошибок работают настоящие. URL строится от `base_url`, редиректы не
разыменовываются молча (`follow_redirects=False`), чтобы редирект можно было
утверждать явно.

**Проверяются не только коды.** Обязательные группы утверждений:

| Группа | Что утверждается |
| --- | --- |
| Статус | `status.HTTP_201_CREATED`, `status.HTTP_401_UNAUTHORIZED`, `status.HTTP_403_FORBIDDEN`, `status.HTTP_404_NOT_FOUND` — из `starlette.status` |
| Заголовки | `Content-Type`, `Cache-Control`, `X-Request-ID`, `Vary`, `Set-Cookie` с флагами `HttpOnly`/`SameSite`/`Secure`, CORS для API-клиента |
| Форма тела | ключи JSON, отсутствие лишних, типизированная форма ошибки `{code, message, details}` |
| Cookie / Bearer | наличие токена в теле для мобильного клиента и в cookie для браузера; отзыв после выхода |
| Состояние базы | после запроса запись действительно появилась, изменилась или удалена — проверка через сессию или репозиторий |
| Последовательный шаг | второй запрос использует результат первого (идентификатор, токен), а не независимо подготовленные данные |

**Внешний мир подменяется на границе.** LLM, Kodik, AniLibria, почта и Telegram
заменяются двойниками на уровне Dishka-провайдеров: E2E не зависит от сети и
квот, но проверяет всю собственную цепочку — включая то, что возрастная политика
отсекает запрос до обращения к модели. Приложением управляется настоящий
`create_app()`, подменяются только зависимости-адаптеры.

**Сброс состояния полный.** Перед сценарием база очищается или заворачивается в
транзакцию прогона, Redis чистится по тестовому префиксу namespace. Сценарий,
которому нужен «чистый первый вход пользователя», обязан получать его явно, а не
благодаря удачному порядку запуска.

**Один файл — одна пользовательская история.** Название файла оканчивается на
`_flow.py`, класс — `Test<Субъект>Flow`, тест — полный путь:
`test_register_login_and_add_favorite`.

### Пример

```python
"""Сквозной сценарий: регистрация, вход, избранное, список."""

from __future__ import annotations

import httpx
import pytest
from starlette import status


@pytest.mark.e2e
class TestAuthenticationFlow:
    """Жизненный цикл сессии и права на избранное через HTTP."""

    async def test_register_login_and_read_favorite(
        self,
        client: httpx.AsyncClient,
        user_payload: dict[str, str],
        read_row,
    ) -> None:
        """Что тестируем: полный путь от регистрации до чтения избранного.
        Что передаём: валидную учётную пару и тайтл, которого нет в каталоге
        пользователя.
        Что ожидаем: регистрация отдаёт 201, вход — Bearer-пару, добавление —
        201 с записью в базе, список содержит добавленный тайтл, аноним получает 401.
        """
        register = await client.post("/api/v1/auth/register", json=user_payload)
        assert register.status_code == status.HTTP_201_CREATED

        login = await client.post(
            "/api/v1/auth/login",
            json={
                "email": user_payload["email"],
                "password": user_payload["password"],
            },
        )
        assert login.status_code == status.HTTP_200_OK
        assert login.headers["content-type"].startswith("application/json")
        tokens = login.json()
        assert tokens["access_token"] and tokens["refresh_token"]
        headers = {"Authorization": f"Bearer {tokens['access_token']}"}

        added = await client.post(
            "/api/v1/favorites",
            json={"anime_id": 185, "title": "Initial D First Stage"},
            headers=headers,
        )
        assert added.status_code == status.HTTP_201_CREATED
        assert await read_row("SELECT count(*) FROM favorites WHERE anime_id = 185") == 1

        listed = await client.get("/api/v1/favorites", headers=headers)
        assert listed.status_code == status.HTTP_200_OK
        assert [item["anime_id"] for item in listed.json()["items"]] == [185]

        anonymous = await client.get("/api/v1/favorites")
        assert anonymous.status_code == status.HTTP_401_UNAUTHORIZED
        assert anonymous.json()["code"] == "unauthorized"
```

Фикстуры `client`, `user_payload` и `read_row` объявляются в
`tests/e2e/fixtures/`; в тесте они только принимаются
([иерархия фикстур](05-fixtures-and-isolation.md)).

### Чек-лист сквозного сценария

- [ ] Сценарий начинается с действия пользователя, а не с подготовленной записи в базе
- [ ] Каждый следующий шаг использует результат предыдущего (токен, идентификатор)
- [ ] Проверены заголовки, а не только тело
- [ ] Проверено состояние базы после записи
- [ ] Проверен отказ: аноним и чужой пользователь
- [ ] Нет обращений к интернету: LLM и провайдеры закрыты двойниками на границе
- [ ] Сценарий воспроизводим при пустой базе и при произвольном порядке запуска
- [ ] Утверждения используют константы `starlette.status`

### Антипаттерны

| Антипаттерн | Чем заменяется |
| --- | --- |
| Прямой вызов сценария внутри «E2E» | вызов через HTTP; прямой вызов — уровень Unit или Integration |
| Утверждение только кода ответа | плюс форма тела, заголовки и состояние базы |
| Подготовка пользователя `INSERT` в тесте | регистрация через маршрут: сценарий проверяется целиком |
| Один тест на пять несвязанных маршрутов | один сценарий — одна история, файлы разделены по субъекту |
| Жёсткий идентификатор из боевой базы | данные создаются шагами сценария или фабрикой |
| Разыменование редиректа по умолчанию | `follow_redirects=False` и явное утверждение о `location` |
| Изолированная проверка CSRF вне приложения | CSRF живёт в middleware и проверяется только сквозным прогоном с реальным запросом на запись |

## Почему это сделано так

E2E проверяет связку, а не правило: единственное, что нельзя увидеть снизу, —
поведение целого приложения, включая порядок middleware, форму ответа и права.
Именно на этом уровне ловится «маршрут отдаёт 200, но заголовок `Set-Cookie`
не доставлен», «CSRF отклоняет живой запрос клиента» и «чужой пользователь
получил чужой ресурс».

Внешний мир закрывается двойниками на границе, а не в середине цепочки: если
подменить сценарий, E2E превращается в тест пустого роутера, и проверка теряет
смысл. Граница же — это адаптер провайдера, и именно она в бою самая
недетерминированная.

Состояние базы проверяется после запроса, потому что HTTP-ответ может быть
успешным при не зафиксированной транзакции: сценарий вернул данные из своей
сессии, а `commit` не произошёл. Ответ об этом не скажет, запрос к базе — да.

Полный сброс перед сценарием, а не точечный откат, нужен из-за кэшей:
`HighlightDashboardCache` переживает запрос, и второй сценарий, стартующий с
чужим состоянием ленты, даёт плавающее падение.

## Где в коде

- `src/backend/presentation/app_factory.py` — точка входа, порядок middleware
- `tests/e2e/` — сквозные сценарии по субъектам
- `tests/e2e/fixtures/` — фикстура клиента с токеном, фикстура чтения базы
- `pyproject.toml` — маркер `e2e`
- `docs/api/openapi.json` — контракт, против которого строятся утверждения о форме
- [Матрица маршрутов](../01-architecture/route-matrix.md) — источник проверок `401`/`403`
