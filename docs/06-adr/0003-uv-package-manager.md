# 0003. uv как менеджер пакетов и окружений

Статус: принято
Дата записи: 2026-10

## Контекст

**AEM** разрабатывается на Windows, проверяется в CI на Ubuntu и исполняется в
контейнере на Debian. Один и тот же `pyproject.toml` обслуживает три среды, а
зависимостей много: SQLAlchemy 2.0, asyncpg и psycopg одновременно, curl-cffi,
redis, dishka, FastAPI, Alembic, плюс инструменты разработки и отдельно
инструменты проверки границ (`grimp`, `import-linter`).

Обычная для таких проектов практика `pip install -r requirements.txt` даёт три
проблемы:

- версии в файле требований не фиксируются транзитивно: сборка образа на другой
  машине тянула другие транзитивные версии, и «не воспроизводится у меня»
  становилось нормой;
- установка десятков пакетов занимала минуты, а пересборка Docker-слоя при
  каждой правке кода удваивала время цикла;
- интерпретатор требовалось заводить вручную: в проекте зафиксирован
  `>=3.12,<3.13`, и разработчик без нужной версии получал синтаксические ошибки
  в коде, рассчитанном на 3.12.

Нужен был один инструмент, закрывающий фиксацию версий, скорость установки,
скачивание интерпретатора и запуск команд в окружении.

## Драйверы решения

| Драйвер | Что требует |
| --- | --- |
| Детерминизм | единый lock-файл, действительный для Windows, Linux и контейнера |
| Скорость | `uv sync` и `uv run` как ежедневные команды, а не редкий выкат |
| Управление Python | версия интерпретатора поднимается автоматически по `.python-version` |
| Разделение групп | инструменты линтера не попадают в боевой образ |
| Простота сборки | в Dockerfile один шаг установки, без `pip` и `requirements.txt` |
| Проверяемость в CI | возможность машинно подтвердить, что lock соответствует манифесту |

## Рассмотренные варианты

| Вариант | Суть | Итог |
| --- | --- | --- |
| `pip` + `requirements.txt` | классическая установка по списку | Отклонён: нет кроссплатформенного lock-файла с хешами, нет управления интерпретатором, группы зависимостей требуют отдельных файлов |
| Poetry | собственный резолвер, `pyproject.toml` + `poetry.lock` | Отклонён: медленнее на больших графах, собственные плагины для venv, конфликт с PEP 735 `[dependency-groups]`, лишние секции (`source`, `group.dev.dependencies`) вместо стандартных |
| pip-tools (`pip-compile`) | генерация lock из манифеста | Отклонён: добавляет шаг ручной перегенерации и отдельный артефакт, интерпретатор не улучшает |
| PDM, Rye | современные менеджеры, близкие по идеям | Отклонён: PDM требует привычки к `pdm run` и отдельному управлению `__pypackages__`, Rye на момент выбора вбирал в себя `uv` как движок и не давал ничего сверх него |
| conda / mamba | окружения с бинарными пакетами | Отклонён: проект чистый Python без нативных библиотек вне PyPI, тяжёлый инструмент не оправдан |
| uv | резолвер и раннер на Rust, `uv.lock`, `uv run`, управление Python | **Принят**: закрывает все шесть драйверов одним инструментом |

## Решение

Инструмент упаковки — uv. Конфигурация в `pyproject.toml`:

| Параметр | Значение | Зачем |
| --- | --- | --- |
| `requires-python` | `>=3.12,<3.13` | интерпретатор зафиксирован с точностью до минорной версии |
| `[tool.uv] required-version` | `>=0.10` | поведение `uv sync` и формат lock различаются между крупными версиями; молча обновить его у разработчика нельзя |
| `python-preference` | `only-managed` | локально uv сам заводит CPython из `.python-version` (3.12.13), системный интерпретатор не используется |
| `default-groups` | `["dev", "lint"]` | `uv sync` ставит pytest, ruff, pre-commit и import-linter без флага |
| `[dependency-groups]` | `dev`, `lint` | группы объявлены по PEP 735, а не специфичной секцией |

Все команды проекта идут через `uv run`, поэтому виртуальное окружение не нужно
активировать ни в терминале, ни в CI:

```bash
uv sync
uv run pytest
uv run ruff check src tests migrations
uv run alembic -c migrations/alembic.ini upgrade head
uv lock --check
```

В образе настройка `only-managed` переопределяется на обратное: переменные
`UV_PYTHON_PREFERENCE=only-system` и `UV_PYTHON_DOWNLOADS=never` заставляют uv
брать интерпретатор базового образа `python:3.12-slim`, иначе скачанный managed
CPython занимал место в слое. Установка выполняется одним шагом
`uv sync --frozen --no-dev --no-install-project --no-cache`, где `--frozen`
запрещает править lock при сборке, `--no-dev` отсекает инструменты разработки,
а `--no-install-project` не пытается собрать само приложение в пакет.
`UV_LINK_MODE=copy` нужен потому, что hardlink из кэша недоступен при переносе
между файловыми системами сборки.

Гейт согласованности — `uv lock --check` в CI: отдельно закоммиченный
`pyproject.toml` без обновлённого `uv.lock` роняет пайплайн.

## Последствия

### Положительные

- один `uv.lock` описывает разрешение версий для Windows, Linux и контейнера;
  сборка образа воспроизводима (`uv sync --frozen`);
- установка и обновление окружения укладываются в секунды, поэтому `uv sync`
  стоит в онбординге первой командой, а не «раз в неделю»;
- версия Python поднимается автоматически: `.python-version` + `only-managed`
  снимают вопрос «какой интерпретатор у тебя локально»;
- группы зависимостей стандартными средствами PEP 735, без плагина и без
  отдельных `requirements-*.txt`;
- в боевом образе нет pip и нет инструментов разработки; сам uv в финальный
  слой не копируется;
- `uv lock --check` делает расхождение манифеста и lock-файла ошибкой сборки.

### Отрицательные

- у всех участников должен быть установлен uv не старше `0.10`; для нового
  разработчика это отдельный шаг, зафиксированный в онбординге;
- `python-preference = "only-managed"` неожиданно для тех, кто привык к
  системному Python: локально появляется интерпретатор, скачанный uv, а не тот,
  что в `PATH`;
- настройка образа обязана держать переопределение `only-system`: без него
  локальная и контейнерная конфигурации расходятся, и это уже было причиной
  раздутого слоя;
- lock-файл плохо читается в диффе: изменение одной зависимости показывает
  переписанные блоки хешей, поэтому ревью читает `pyproject.toml`, а `uv.lock`
  проверяет только гейт `uv lock --check`;
- uv моложе pip и poetry по части API: переход на новую крупную версию требует
  проверить формат lock и флаги сборки.

## Условия пересмотра

Решение пересматривается, если:

- потребуется публикация пакета в реестр с метаданными, которых uv не умеет
  (редкий для приложения случай);
- CI-инфраструктура хостинга лишит возможности ставить бинарный инструмент, и
  останется только pip;
- проект перерастёт в monorepo с несколькими distributions, где понадобится
  workspace-модель, не доступная выбранной версии uv.

## Где в коде

- `pyproject.toml` — `[tool.uv]`, `[dependency-groups]`, `requires-python`
- `uv.lock` — единый lock-файл
- `.python-version` — `3.12.13`
- `Dockerfile` — шаги сборки с `UV_*` переменными
- `.github/workflows/ci.yml` — `astral-sh/setup-uv`, `uv sync --frozen`, `uv lock --check`
- `Makefile` — обёртки `install`, `lock`, `lock-check`, `lock-upgrade`
