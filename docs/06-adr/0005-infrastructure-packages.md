# 0005. Раскладка `infrastructure/` по назначению

Статус: принято
Дата записи: 2026-10

## Контекст

Каталог `infrastructure` вырос из Flask-эпохи **AEM** и смешивал разные
ответственности в одном месте:

- `infrastructure/files/` содержал одновременно `database.py` (engine, `init_db`,
  `verify_schema`), `uploads.py` (файловое хранилище), шаблоны и `scripts/`;
- `infrastructure/models/` лежал рядом с репозиториями, но сами репозитории жили
  в отдельном `infrastructure/repositories/`;
- медиа-прокси занимал верхнеуровневый `infrastructure/media_proxy/`, хотя по
  природе это внешняя интеграция с CDN;
- `infrastructure/web/` держал Jinja2-рендеринг, то есть принадлежал слою
  presentation.

Такая раскладка заставляла искать код «по типу файла», а не по назначению, и
порождала глубокие импорты вида `infrastructure.files.database`, которые нельзя
переименовать без обхода всех мест использования.

## Драйверы решения

| Драйвер | Что требует |
| --- | --- |
| Предсказуемый путь импорта | по имени каталога понятно, что внутри и какого слоя это касается |
| Малая глубина ссылок | наружу — фасад пакета, а не путь к внутреннему модулю |
| Согласованность со слоями | то, что относится к представлению, не живёт в инфраструктуре |
| Проверяемость границы | контракт «Presentation does not reach Infrastructure» должен читаться по структуре каталогов |
| Расширяемость интеграций | новый провайдер видео или каталога добавляется в своё место без раскопок |

## Рассмотренные варианты

| Вариант | Суть | Итог |
| --- | --- | --- |
| Оставить `files/`, `models/`, `web/` | минимальный дифф | Отклонён: сохраняет главную проблему — по имени каталога нельзя сказать, что внутри, а `database.py` рядом с `uploads.py` вводит в заблуждение |
| Разложить по типам классов | `repositories/`, `models/`, `clients/`, `services/` | Отклонён: каждая фича размазывается по трём-четырём каталогам, а «клиенты» смешивают каталоги, видео, LLM и уведомления в одну кучу разной природы |
| Разложить по провайдерам | `kodik/`, `anilibria/`, `gemini/` | Отклонён как основной: зоны данных (`user`, `watch`, `highlight`) пересекают провайдеров, а детали конкретных поставщиков уже вынесены в `external/<домен>/` |
| Разложить по назначению | восемь каталогов, каждый — про одну ответственность | **Принят**: имя каталога отвечает на вопрос «зачем», а не «из чего» |

## Решение

`infrastructure/` разложен по назначению:

| Каталог | Назначение |
| --- | --- |
| `database/` | `session.py`, `unit_of_work.py`, `models/<зона>/`, `repositories/<зона>_repository/` |
| `external/` | интеграции с внешним миром: `catalog/`, `video/` (включая `hls_proxy/`, `ru/`, `adult/`, `kodik/`), `llm/`, `mapping/`, общий `_common/` |
| `cache/` | `KeyValueStore`, TTL-кэш, предметные кэши (рекомендации, дашборд, профиль, источники) |
| `security/` | JWT, bcrypt, CSRF, блок-лист токенов, rate limiter, блокировка входа |
| `storage/` | файловое хранилище изображений |
| `notifications/` | `email/` (отправщики) и `telegram.py` |
| `health/` | пробы готовности и работоспособности |
| `di/` | провайдеры Dishka (`providers/`) и сборка контейнера |

Дополнительные правила:

1. Каталоги `files/`, `models/`, `repositories/`, `web/`, `media_proxy/` и
   `scripts/` внутри `infrastructure` отсутствуют; одноразовые скрипты живут в
   корневом `scripts/`.
2. Рендеринг шаблонов — `presentation/web/templating.py`, сами шаблоны —
   `src/frontend/templates`.
3. Каждый пакет публикует наружу фасад `__init__.py` с `__all__` и докстрингом:
   внешний код импортирует пакет, а не внутренний модуль. Пакет репозитория
   содержит реализацию в модуле по имени зоны данных (`favorites.py`,
   `watch.py`, `support.py`) и переэкспортирует класс фасадом.
4. HLS-прокси — внешняя интеграция (`external/video/hls_proxy/`), а не отдельный
   слой, и именно поэтому его импорт является разрешённым исключением в
   контракте forbidden.
5. Модули, начинающиеся с `_` (`_common/`), — внутренние для родителя: их не
   переэкспортируют фасады верхнего уровня.

## Последствия

### Положительные

- пути импортов предсказуемы: `infrastructure.database.session`,
  `infrastructure.external.video.hls_proxy`, `infrastructure.storage.image_storage`;
- границы слоёв проверяются контрактом import-linter, а исключения (их два)
  читаются как карта реальных компромиссов;
- Alembic читает модели из `infrastructure/database/models` — единственного
  места, где описана схема;
- структура тестов повторяет структуру инфраструктуры
  (`tests/unit/infrastructure/{storage,external,cache,...}`), поэтому отсутствие
  теста на новый модуль видно сразу;
- новая внешняя интеграция добавляется в `external/<домен>/` и не спорит с
  соседями за место в плоском списке.

### Отрицательные

- часть каталогов миниатюрна (`health/` — один класс, `storage/` — один), и
  восемь каталогов верхнего уровня труднее обозревать глазами, чем пять крупных;
- правило «фасад вместо глубокого импорта» требует поддерживать `__init__.py`
  каждого пакета: забытый реэкспорт модели означает, что Alembic её не увидит;
- деление по назначению не совпадает с делением по зонам домена, поэтому в
  `database/repositories/` и `external/video/` применяются разные критерии
  вложенности, и это надо помнить при добавлении файла.

## Условия пересмотра

Решение пересматривается, если:

- в `infrastructure` появится зона с собственным жизненным циклом (очереди,
  воркеры, фоновые планировщики) — её нельзя выразить текущей восьмёркой
  каталогов;
- `external/` превысит разумный размер и потребует деления по типу протокола
  (HTTP API, файловые протоколы, потоковое видео);
- количество миниатюрных каталогов сделает навигацию дороже выгоды — тогда
  допустимо сливать `health/` и `storage/` в соседние области.

## Где в коде

- `src/backend/infrastructure/` — восемь каталогов назначения
- `src/backend/infrastructure/external/` — `catalog`, `video`, `llm`, `mapping`, `_common`
- `src/backend/infrastructure/database/repositories/` — пакеты репозиториев с фасадом
- `src/backend/presentation/web/templating.py` — рендеринг, переехавший в presentation
- `migrations/env.py` — чтение метаданных из `infrastructure.database.models`
