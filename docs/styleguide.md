# Стайлгайд: работа с проектом и репозиторием

## Описание

Этот документ — единый свод правил для разработки в **Anime Epic Moments**: как настроить окружение, какие команды
использовать, как писать код, тесты, коммиты и проходить CI. Все правила закреплены конфигами в репозитории
(`pyproject.toml`, `ruff.toml`, `.github/workflows/ci.yml`) или описаны здесь как обязательные практики.

## Как это работает

### Инструменты

Проект использует **uv** как единый инструмент управления Python и зависимостями. `pip`, `requirements.txt` и
`venv` **не используются** — не добавляйте новые requirements-файлы и не устанавливайте пакеты через pip.

Установка uv (один раз, локально):

```powershell
irm https://astral.sh/uv/install.ps1 | iex
```

Минимальная версия uv указана в `pyproject.toml`: `[tool.uv] required-version`.

### Виртуальное окружение и зависимости

- Окружение создаётся и обновляется командой `uv sync`. Она создаёт `.venv`, устанавливает зависимости и
  активирует dev-группу.
- Всё, что нужно для запуска и тестов, описано в `pyproject.toml`:
  - `[project] dependencies` — рантайм-зависимости (FastAPI, SQLAlchemy, и т.д.), зафиксированы по версиям;
  - `[dependency-groups] dev` — pytest, pytest-asyncio, pytest-cov, ruff;
  - `[dependency-groups] lint` — import-linter, grimp;
  - `[tool.uv] default-groups = ["dev", "lint"]` — обе группы ставятся по умолчанию.
- Файл `uv.lock` зафиксирован в репозитории: lock-файл трогать вручную нельзя, он обновляется только через
  `uv lock` / `uv add`.
- Новая зависимость: `uv add <пакет>` (или `uv add --dev <пакет>`, `uv add --group lint <пакет>`).
  Вместе с установкой автоматически обновится `uv.lock`.
- Изменение версии или состава зависимостей **должно** сопровождаться свежим `uv.lock` в том же коммите,
  иначе `uv sync --frozen` упадёт в CI.

### Команды

| Действие                   | Команда                                            |
|----------------------------|----------------------------------------------------|
| Установить окружение       | `uv sync`                                          |
| Обновить окружение         | `uv sync --frozen` (если lock уже актуален)        |
| Запустить приложение       | `$env:PYTHONPATH="src"; uv run python -m backend.main` |
| Запустить тесты            | `uv run pytest`                                    |
| Быстрые тесты (без coverage)| `uv run pytest -q --no-cov`                        |
| Линт                        | `uv run ruff check src tests`                      |
| Проверка форматирования    | `uv run ruff format --check src tests`             |
| Автоформат                 | `uv run ruff format src tests`                     |
| Проверка границ слоёв      | `$env:PYTHONPATH="src"; uv run lint-imports`       |
| Миграции БД (Alembic)      | `uv run alembic -c build/alembic/alembic.ini upgrade head` |

Псевдонимы этих команд есть в `Makefile` (`make install`, `make lint`, `make test`, `make check-imports`).

### Порядок работы

1. Создай `.env` из `.env.example` и заполни значения (`Copy-Item .env.example .env`).
2. `uv sync` — установить окружение.
3. Внеси изменения в код, сопровождая их тестами.
4. Перед коммитом обязательно прогнать локальные гейты (см. ниже).
5. Открыть PR — CI прогонит те же гейты.

### Локальные гейты перед коммитом

Эти команды должны проходить без ошибок (то же самое выполняет CI):

```powershell
uv run ruff check src tests
uv run ruff format --check src tests
$env:PYTHONPATH="src"; uv run lint-imports
uv run pytest -q --no-cov
```

### Git-процесс

- Ветки: `main` — стабильна. Фичи и фиксы делаются в отдельных ветках (`feature/...`, `fix/...`),
  вливаются через pull request (или напрямую в `main`, если вы работаете solo и PR не используете).
- Коммиты: сообщение краткое, начинается с глагола в повелительном наклонении (add / fix / refactor /
  update), отражает суть изменения. Например: `fix: пропускать primary LLM без API-ключа`.
- Один коммит — одна логическая единица работы. Чистку формата (ruff format) удобно выносить в отдельный
  коммит, чтобы не смешивать с изменениями логики.
- Не коммить: `.env`, секреты, случайные артефакты. Всё лишнее уже в `.gitignore`.
- Перед коммитом проверь `git status` и `git diff` — в проде (или ревью) попадает только то, что ты видишь.
- **CORS/SMTP/API-ключи в коде и конфигах — запрещено.** В `.env.example` — только заглушки.

## Код

### Структура и слои

```
src/backend/
  presentation/     HTTP-слой: routes, мапперы запросов/ответов (только перевод HTTP → use case)
  application/      use cases и application-сервисы (оркестрация, DTO-команды/результаты)
  domain/           сущности, value objects, политики, интерфейсы репозиториев и сервисов
  infrastructure/   реализация граничных зависимостей: БД, внешние API, кэш, безопасность, DI
  config/           чтение настроек из окружения
  utils/            вспомогательные утилиты без бизнес-логики
  main.py           точка входа: create_app(), uvicorn
src/frontend/       шаблоны, статика
tests/              unit/ (без внешнего IO), integration/ (реальные БД/роутеры)
build/              Docker, Alembic, docker-compose, entrypoint
docs/               документация
```

Границы слоёв закреплены контрактом **import-linter** `Layer Boundaries`
(`presentation → infrastructure → application → domain`): домен не знает о FastAPI и SQLAlchemy,
инфраструктура не знает о презентации. Нарушение падает в `lint-imports`.

### Python-код

- Формат: ruff (config в `ruff.toml`). Применяй `uv run ruff format` перед коммитом.
- Линт: включены E/W/F/I/N/D/UP. Часть правил выключена как legacy-долг (`D101–D103` — отсутствие docstring в
  старых классах/методах, `E501` — длинные строки) — **для нового кода они не отменены**:
  - публичные модули, классы, методы и функции пишутся с docstring в стиле Google
    (summary, Args, Returns);
  - строка — до ~100 символов, длинные выражения переноси;
  - не злоупотребляй исключениями: если для своего кода пришлось отключить правило на уровне файла —
    это повод обсудить на ревью, а не молча обойти.
- Типизация: аннотации типов обязательны для публичных сигнатур.
- Исключения: доменные ошибки — свои классы в `domain/.../exceptions.py`, а не голые `Exception`
  и не HTTP-зависимые ошибки в домене.
- Не импортируй `*` (F403/F405 в линте).
- Без комментариев-«спама»: код должен объяснять себя, комментарии — только где контекст незаметен.

### Тесты

- Тесты живут в `tests/`, структура зеркалит `src/backend/`.
- Марки: `@pytest.mark.unit` (чистая логика, моки), `@pytest.mark.integration` (реальные БД/репозитории),
  `@pytest.mark.e2e` (полные HTTP-сценарии).
- Async-тесты — обычные `async def`-тесты, pytest-asyncio в режиме `auto`.
- Новый use case / route / граничное действие сопровождается тестами в том же PR.
  Изменение базы → миграция Alembic + тест репозитория.
- Coverage включён при `uv run pytest` (`--cov=src`) и должен не проседать без причины.

### Конфигурирование

- Новый параметр окружения: добавь функцию чтения в `src/backend/config/sections/` (или существующую секцию),
  подключи в `src/backend/config/settings.py`, добавь строку с комментарием в `.env.example`.
- Секреты читаются только из окружения через `Settings`, в коде — доступ через `backend.config.Settings`.

## Почему это сделано так

- uv — один инструмент вместо pip+venv+pip-tools: быстрые установки, детерминированный lock, единые команды.
- Гейты в CI совпадают с локальными — человек не попадает в «работает у меня, но не деплоится».
- Границы слоёв и линт ловят архитектурный и стилевой регресс автоматически, а не на ревью.
- Долг по docstring/длине строк учтён и отключён точечно, чтобы не блокировать работу, но новые файлы
  пишутся сразу по правилам.

## Где в коде

- `pyproject.toml` — зависимости, группы, pytest, import-linter, coverage
- `ruff.toml` — конфиг линта
- `.github/workflows/ci.yml` — гейты CI
- `Makefile` — сокращения команд
- `build/Dockerfile`, `build/docker-compose.yml` — упаковка и запуск
- `docs/conventions.md` — соглашения об архитектуре
- `docs/onboarding.md` — быстрый старт для нового разработчика
